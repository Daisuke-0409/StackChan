## 1. やりたいこと

大輔が、事務所や車の中で、タチコマ (音声対話ロボット) にこう聞きます。

```
「最近受けた案件で、加江田のお客さんで、俺の担当のお客さんいなかったっけ？
  電話番号教えて」

  → 「◯◯さんですね。電話番号は090-…だよ」

「それモニターに出して」

  → CRM の画面にその人のカルテが開く
```

前半が**探す**、後半が**出す**。それぞれ口が1本ずつ要ります。

---

## 2. 材料はすでに CRM の中にあります

`schema.sql` と `server.py` を読んで確認した範囲では、**新しいテーブルも新しい
データ収集も不要**です。

| 欲しい条件 | 既にある場所 |
|---|---|
| 地区 (加江田) | `grave_sites.area` |
| 担当者 (俺=ダイスケ) | `cases.sales_staff` / `cases.staff_normalized` (索引あり) |
| 最近受けた | `cases.order_date` |
| 電話番号 | `customer_phones.phone` |
| 顧客の識別子 | `customers.customer_id` |

既存の `field_search()` の JOIN 構造がほぼそのまま使えるはずです。

## 3. 依頼 1: 条件で探す

```
GET /api/tachikoma/find?area=&staff=&since=&name=&asked_by=
X-Tachikoma-Token: <既存と同じトークン>
```

### 引数 (すべて省略可、ただし最低1つは必須)

| 引数 | 例 | 内容 |
|---|---|---|
| `area` | `加江田` | 地区。`grave_sites.area` の部分一致でよい |
| `staff` | `ダイスケ` | 担当者。**CRM 側の名寄せ規則を適用してください** (大輔=ダイスケ など、既に CRM が持っているもの) |
| `since` | `2026-06-01` | この日以降に受注した案件に限る (`cases.order_date`) |
| `name` | `山田` | 既存 lookup と同じ名前検索。併用できると便利です |
| `asked_by` | `ダイスケ` | 声紋で識別した照会者。未指定・未知は `unknown` で処理続行 |

条件が1つも無いときは **400** で構いません (全件返す口にはしないでください)。

### 返す項目

```json
{
  "count": 4,
  "results": [
    {
      "customer_id": 1234,
      "customer_name": "山田 久美子",
      "phone": "090-xxxx-xxxx",
      "cemetery_name": "みたまA-12"
    }
  ]
}
```

**この4項目以外は返さないでください。**住所・故人名・受注日・金額・施工者名・
写真は不要です。

`count` は総数、`results` は**先頭3件まで** (既存 lookup と同じ)。
該当なしは `{"count": 0, "results": []}`。

### `phone` について

電話番号は、霊園名より**重い開示**だと考えています。理由は2つ:

1. タチコマは**声に出して読み上げます**。部屋にいる全員に聞こえます
2. 墓所は現場で必要な情報ですが、電話番号は連絡先そのものです

そこでお願いが2つあります。

- **audit_log に「電話番号を返した」ことが分かる形で記録してください。**
  墓所照会と同じ行に混ぜず、区別できるようにしていただけると助かります
- 複数の電話番号がある顧客は、**代表1件だけ**返してください
  (どれを代表とするかは CRM 側の判断で構いません)

タチコマ側では、**声紋で本人と確認できた場合にのみ**読み上げる実装にします。
識別できなかった相手には電話番号を答えません。

## 4. 依頼 2: 画面に出す

```
GET /api/tachikoma/show?customer_id=&asked_by=
X-Tachikoma-Token: <同じトークン>
```

タチコマは `customer_id` を渡すだけで、**返ってくるのは「開くべきURL」1本**です。

```json
{"url": "http://127.0.0.1:8765/karte?key=...&customer_id=1234"}
```

タチコマ側は、そのURLを**会社PCのブラウザで開く**だけです。中身は見ません。

### 現状の確認

`app.js` を読んだ限り、**現在の画面はURLで特定の顧客を開けません**
(`URLSearchParams` は API クエリの組み立てにしか使われていませんでした)。
なので何らかの追加が要ります。実装方法は**どちらでも構いません**:

- (a) 既存の画面が `?customer_id=1234` を読んで、その人のカルテを開いた状態で起動する
- (b) 表示専用の新しいページを作る (職人さん用の `/genba?key=…` と同じ考え方)

**(b) の前例があるので、そちらが楽ならそれで結構です。**

### なぜ「URLを返す」形にしたいか

タチコマが持つのは **`customer_id` という整数1つだけ**になります。
顧客の中身は CRM から画面へ直接出て、**タチコマのプロセスを一度も通りません**。

読み上げよりも開示が少ない経路です。「モニターに出して」の方が
「電話番号教えて」より安全、という関係になります。

### 監査

表示も1行残してください。「誰が」「いつ」「誰のカルテを開いたか」。

## 5. 認証・その他

- 認証は**既存と同じ `X-Tachikoma-Token`** で結構です。新しいトークンは不要です
- **`is_local()` は復活させないでください** (前回と同じ理由。NAS 移設で意味を失います)
- 新しい依存は不要のはずです。**標準ライブラリのみ / pip 禁止**の方針のままで足ります
- **既存の認証・画面・APIには手を触れないでください。**足すのは2本だけです
- 書き込みは一切不要です。**どちらも読み取り専用**にしてください

## 6. こちらで決められないこと (実装せず質問を返してください)

1. **`staff` は `sales_staff` と `staff_normalized` のどちらで照合すべきか。**
   名寄せ規則 (大輔=ダイスケ、一木=会長、2025年以前の「社長」=いまの会長) を
   適用した後の値で引きたいのですが、どちらの列がその役割か判断できませんでした

2. **「最近」を CRM 側で解釈すべきか。**
   タチコマ側で「最近」→ `since=2026-06-01` のように日付へ変換して渡すつもりですが、
   業務上「最近」に決まった意味があるなら (例: 当月・直近3ヶ月)、
   CRM 側の既定値として持っていただく方が正確です

3. **電話番号を返すこと自体に、会長・社長の承認が要るか。**
   音声で読み上げる以上、これまでの画面越しの閲覧とは性質が違います。
   必要なら、こちらの実装を止めて待ちます

## 7. できたことの確認方法

```
curl -H "X-Tachikoma-Token: <トークン>" \
  "http://127.0.0.1:8765/api/tachikoma/find?area=加江田&staff=ダイスケ&since=2026-06-01&asked_by=ダイスケ"

curl -H "X-Tachikoma-Token: <トークン>" \
  "http://127.0.0.1:8765/api/tachikoma/show?customer_id=1234&asked_by=ダイスケ"
```

- `find` が 4項目だけ返る (住所・故人名・写真が返らない)
- `find` の条件を1つも付けないと 400
- `show` が返した URL をブラウザで開くと、その顧客のカルテが表示される
- audit_log に2行増える。**電話番号を返した照会と、カルテを開いた操作が区別できる**
- トークン無し・誤りで 403

## 8. NAS 移設について

前回と同じで、**タチコマ側の変更は接続先ホストだけ**になるよう作ってあります。
`show` が返す URL のホスト名も、移設後は NAS のホスト名になる前提で構いません
(タチコマは受け取った URL を開くだけなので、こちら側の変更は不要です)。

## 9. 参考: 既に動いているもの

前回実装いただいた `/api/tachikoma/lookup` は、タチコマ側で
**2ターンの絞り込み**に対応しました。「山田さんの墓どこ？」→「6件あるよ、
下の名前を教えて」→「太郎」→ 1件に確定、という往復です。

`find` も同じように、件数が多いときは条件を足して聞き直す形にします。
`count` が総数であることが、その聞き返しの根拠になっています。
