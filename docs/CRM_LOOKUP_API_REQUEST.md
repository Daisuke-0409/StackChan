## 1. 何をしたいか

タチコマ (音声対話ロボット) に「**◯◯さんのお墓どこ？**」と声で聞くと、
霊園名と区画を声で答える。それだけです。

現場でスマホを出せないとき、運転中、手が塞がっているときに使います。

---

## 2. なぜ既存の `/api/field/search` をそのまま使わないか

使えば動きます。ただし返ってくる量が、目的に対して大きすぎます。

`field_search()` が1件あたり返すもの:

```
case_id, deceased_name, order_date, case_status,
customer_name, address,
cemetery_name, area, builder_name, zenrin_map_no,
grave_site_id, latitude, longitude, gps_updated_at,
photos[] (document_id, file_name, stored_name, category)
```

これが**最大20件**。対してタチコマが読み上げに使うのは **霊園名と区画** だけです。

タチコマ計画には「**モデルに秘密を渡さない**」という原則があります。
聞いてはいけない事実は、そもそもコンテキストに載せない。プロンプトで「言うな」と
指示する方式は、同情的な聞き方で引き出される余地が残るからです。

同じ理屈が、この境界にも当てはまります。**タチコマのプロセスが受け取らなければ、
タチコマが漏らすことはできません。** 逆に、住所・故人名・受注日・施工者名・
写真ファイル名を20件ぶん受け取ってしまうと、「漏らさない」がタチコマ側の実装の
正しさに依存することになります。それは弱い保証です。

もうひとつ、CRM 側の掟との衝突があります。

> **ログインは個人単位**（名前を選んで個人PIN）。共有合言葉に戻さない。
> 「誰が」の記録が全機能の土台になっている

タチコマは声紋で話者を識別しているので、**誰が聞いたかを渡せます**。
それを audit_log に残せるのは CRM 側だけです。

### 補足: `is_local()` は現在デッドコードです

2026-08-19 に `server.py` を確認したところ、**`is_local` は全体で1回しか現れません**
(4125行の定義のみ)。呼び出し箇所はゼロです。個人PINログイン導入 (2026-08-07) の際に
使われなくなったものと思われます。`require_auth()` が `/api/` 配下すべてに
セッションを要求し、`127.0.0.1` からでも **401** が返ります (実測済み)。

タチコマ計画側は7月の調査時点の「ローカルからは認証不要」という前提で設計を
始めていましたが、**その前提はもう成立しません**。これが、新エンドポイントに
独自のトークンをお願いしている直接の理由です。

代替案として「タチコマに誰かの個人PINを持たせる」ことも技術的には可能ですが、
**採用しません**。人の資格情報をロボットに持たせることになり、かつ全ての照会が
その人の名前で記録されてしまうためです。CRM が土台と位置づけている「誰が」を
壊す方向の解決策は取りません。

## 3. 依頼するもの

読み取り専用のエンドポイントを1本。

```
GET /api/tachikoma/lookup?name=<氏名>&asked_by=<照会者名>
```

### 入力

| 引数 | 必須 | 内容 |
|---|---|---|
| `name` | 必須 | 探す人の名前。表記ゆれ込み (既存の `field_search` と同じ正規化でよい) |
| `asked_by` | 必須 | **声で聞いた人の名前**。タチコマが声紋で識別した結果を入れます。未識別なら `unknown` |

`address` での検索は今回は要りません (声で住所を言うことは想定していない)。
必要になったら追加で依頼します。

### 出力

```json
{
  "count": 1,
  "results": [
    {
      "customer_name": "◯◯ ◯◯",
      "cemetery_name": "◯◯霊園",
      "area": "12区3側",
      "zenrin_map_no": "..."
    }
  ]
}
```

**これ以上は返さないでください。** 特に次は不要です:

- `address` (施主住所)
- `deceased_name` (故人名)
- `order_date` / `case_status` / `builder_name`
- `photos[]`
- `latitude` / `longitude` — 声で読み上げないため。
  ナビ連携をやる段階になったら改めて依頼します

`customer_name` を返してほしいのは、同姓の候補が複数出たときに
「◯◯さんが2人います」と聞き返すためです。

### 件数

3件を上限にしてください。声で読み上げるので、それ以上は返しても使えません。
4件以上該当した場合は `"count": 7, "results": [先頭3件]` のように、
**総数は正しく返して results だけ切る**形でお願いします
(「7人いるので絞ってください」と言えるようにするため)。

### 該当なし

`{"count": 0, "results": []}`。エラーにしないでください。

## 4. 認証と監査

**重要: CRM は将来 NAS に引っ越す予定です。** そのとき呼び出し元は別ホストになり、
`is_local()` は成立しなくなります。引っ越しで作り直しにならないよう、
**最初からトークンで認証してください。**

- **`X-Tachikoma-Token` ヘッダの一致で許可**してください。不一致・未指定は 403。
  トークンは `config.json` に1つ持たせてください (既存のパスワード類と同じ扱い、git に入れない)
- **`is_local()` を復活させないでください。** 呼び出し元が同じPCかどうかは、
  NAS 移設で意味を失います。トークン1本で判断してください
- トークンが漏れたときに差し替えられるよう、**`config.json` の値を読み直せば効く**
  形にしてください (再起動で構いません)
- `asked_by` が空、または未知の名前のときは **`unknown` として処理を続け、
  その旨を audit_log に残す**でください。拒否はしないでください
  (声紋が外れただけで現場が止まると困るため)
- **audit_log に1行残してください。** 「誰が」「いつ」「誰を照会したか」。
  操作ログは追記のみという既存の方針のままで結構です

## 5. やらなくていいこと

- 画面・UI は不要です。API 1本だけです
- 書き込み系は一切不要です。**読み取り専用**にしてください
- 新しい依存は不要です (既存の `field_search` の結果を絞るだけで実装できます)。
  **標準ライブラリのみ / pip 禁止**の方針はそのままで足ります
- **既存の認証の作りは変えないでください。** 個人PINログインも `is_local()` も
  そのままで結構です。新エンドポイントを1本足し、**その1本の中だけで**
  トークン検査をしてください (4章)。他の画面・APIには手を触れないでください

---

## 6. できたことの確認方法

CRM を起動した状態で、同じPCから:

```
curl -H "X-Tachikoma-Token: <config.json に入れた値>"   "http://127.0.0.1:8765/api/tachikoma/lookup?name=<実在する名前>&asked_by=ダイスケ"
```

- 霊園名と区画が返る
- **住所・故人名・写真が返らない**
- audit_log に照会の記録が1行増えている
- トークン無し、または間違ったトークンで叩くと 403
- 正しいトークンなら、別PCから叩いても通る (NAS 移設後の経路の先取り確認)

## 7. 質問と回答の窓口

仕様で迷った点は、実装で埋めずに質問を返してください。特に:

- `area` (区画) の表記が台帳内で揺れている場合、声で読める形に整える必要があるか
- 同姓同名が同じ霊園にいる場合の区別のしかた

タチコマ側は、このエンドポイントが無い間は既存の `/api/field/search` を叩いて
必要な項目だけ抜く暫定実装で進めます。**このエンドポイントができ次第、
そちらに切り替えて暫定実装は捨てます。**
