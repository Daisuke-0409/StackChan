## 1. コンセプト (不変)

**人格は1つ、入口は複数。**

タチコマという1つの人格 — 記憶・権限・声・感情 — に対して、StackChan 実機・PC・
Even G2 スマートグラス・会社システムなど複数の入口からアクセスする。
どの入口から話しても同じ相手であり、同じ過去を共有する。

守っている原則は3つ。

1. **デバイスに AI は載せない。** 頭は家の PC のゲートウェイ1つ。API キーは PC 側にのみ置く
2. **秘密は「守らせる」のではなく「渡さない」。** 聞いてはいけない事実はモデルの
   コンテキストに載せない。プロンプトで「言うな」と指示する方式は、同情的な聞き方で
   引き出される余地が残る
3. **記憶は人格に紐づく。** 機体は応答先の単位でしかない

## 2. 全体アーキテクチャ

```
            入口                              頭                     記憶
  +---------------------+      +------------------+      +--------------+
  | StackChan 実機 x2    |      |                  |      | tachikoma    |
  |  家 80:45:6B:4D:E0:3C| ---> |  Gateway         | ---> |  .json       |
  |  会社 ...:E7:AC      |      |  (家のPC:8080)   |      | people.json  |
  +---------------------+      |                  |      | settings.json|
  | PCの耳 (USBマイク)   | ---> |  Gemini          |      +--------------+
  +---------------------+      |  VOICEVOX (TTS)  |
  | Even G2 (声→文字)    | ---> |  声紋・顔認識     |      +--------------+
  +---------------------+      |  権限判定         | ---> | orderagent   |
  | ブラウザ / スマホ     | ---> |  感情判定         |      | (:8766)      |
  +---------------------+      |                  |      +--------------+
  | Claude Code (承認)   | <--> |                  |
  +---------------------+      +------------------+
                                        ^
                          Tailscale     |
  会社の体 --(会社LAN)--> 会社PC の転送役 +   (認証も保存もしない中継のみ)
```

**会話の流れ (実機):**

```
頭タッチ(押下→離す) → 録音(最大30秒) → POST /v1/transcribe (Gemini STT + 話者識別)
  → POST /v1/chat (Gemini + Google検索 + 記憶 + 権限フィルタ)
  → 文ごとに TTS (ローカル VOICEVOX) → speak_queue に積む
  → デバイスが200ms間隔でポーリングして取得 → 再生 + 感情モーション
```

発話終了から最初の音声まで **約3.7秒**。

### ゲートウェイのエンドポイント

| エンドポイント | 用途 |
|---|---|
| `POST /v1/transcribe` | 音声→テキスト。話者識別もここ |
| `POST /v1/chat` | 返答生成。記憶・検索・権限・感情タグ |
| `GET /v1/speak_queue` | デバイスが返答音声を取りに来る。`X-Tachikoma-Emotion` ヘッダ付き |
| `POST /v1/speak` | 任意テキストを喋らせる |
| `POST /v1/announce` | テキスト読み上げ (文分割TTS)。承認デーモン・注文エージェントが使う |
| `POST /v1/vision` | カメラフレーム。顔検出・顔認識 |
| `GET/POST /v1/people` | 登録済みの人 (声紋・顔・役割) |
| `GET/POST /v1/settings` | 設定 |
| `POST /v1/location` | iPhone ショートカットからの GPS |

## 3. 機能カタログ

### 3.1 会話 (完成・実用)

| 機能 | 内容 |
|---|---|
| 音声対話 | 頭を押して離す = 録音。最大30秒。発話終了から初音声まで約3.7秒 |
| ハンズフリー継続 | 返事のあと約30秒、頭を触らずに続けて話せる (2026-08-15 達成) |
| 会話の記憶 | 直近10往復 + 恒久的な事実 (名前・居住地・勤務先・誕生日)。事実抽出は**返答送信後にバックグラウンド**で走るので待ち時間に乗らない |
| Web検索 | Gemini の google_search グラウンディング。必要な質問だけ自動で検索し、通常会話の速度は落ちない |
| ローカルTTS | VOICEVOX (ずんだもん、1文約755ms)。エンジン未起動なら Gemini TTS に自動フォールバック |
| 自声ガード | タチコマが自分の返事に反応して喋り出さないようにする |

### 3.2 権限と記憶 (ゲートウェイ側は完成)

| 機能 | 内容 |
|---|---|
| 話者識別 | 声紋で誰が話しているかを判定。score>=0.75 の一致でサンプルを自動追加 (最新8件保持) |
| 顔識別 | 会話中 (Listening/Thinking/Speaking/Reacting) だけ約700ms間隔でフレームを送る |
| 記憶の可視性制御 | 相手ごとに記憶を出し分ける。**聞いてはいけない事実はコンテキストに載せない** |
| 秘密指定 | 「ここだけの話」等のキーワード。**直前の会話にも遡って**適用される |
| 記憶の人格化 | 保存先は機体MACではなく人格 (`tachikoma.json`)。`TACHIKOMA_MEMORY_SCOPE=device` で旧挙動に戻せる |
| 記憶の統合 | `merge_memory.py`。**機械は順序を推測しない** — 会話に時刻が無いため、2つある場合は人が決める。`--write` 無しでは何も書かない |

**誰も登録されていない間は全員 master 扱い**。これは意図的で、そうしないと本人が
自分の記憶を見られない。誰か登録された時点で制御が始まる。

### 3.3 感情表現 (完成)

```
モデルが回答の先頭に [happy]/[sad]/[neutral] を必ず付ける
  → _split_emotion_tag() がタグを剥がす
  → happy→happy, sad→confused (neutral は意図的に無反応)
  → 機体ごとに保留 → /v1/speak_queue の X-Tachikoma-Emotion ヘッダで返す
  → speech_announcer.cpp がヘッダを読み、モーションを直接再生
```

**タグは音声より先に決まる**ので、文が1つも合成される前に動きを始められる。
動きの大型化 (範囲3倍・整定時間調整) も完了済み。**残作業は無く、次は実機で目視確認するだけ**。

注意: モーションは状態機械を経由しない。`HappyRequested`/`ConfusedRequested` は
`Reacting` へ遷移するが `Reacting`+`SpeechFinished` の規則が無いため、
発話中に使うと `Speaking` から抜けられず `Error` に落ちる。

### 3.4 入口 (実機以外)

| 入口 | 状態 | 内容 |
|---|---|---|
| **PCの耳** (R2) | 実機確認済み | USBマイクで聞き、返事は**タチコマの口とモーション**で返す。`device_id` を実機と同じにすることで記憶・権限・感情がそのまま効く |
| **Even G2** (R5) | 会話成立確認済み | メガネ = **ゲートウェイがホストする Web ページ**。新しい頭は不要。**スピーカー無し・カメラ無し・マイクあり** → 「声で話しかけて文字で返る」。顔認識は使えないが声紋は使える |
| **Even Terminal** | 稼働中 | Claude Code / Codex のセッションをメガネに流す**公式機能**。ポート3456、ログオン時タスク化済み |
| **ブラウザ/スマホ** | 稼働中 | 設定アプリ・操作ページ。Tailscale HTTPS で配信 |
| **会社の体** | 経路構築済み | 会社PCの転送役ごしに家の頭へ (下記 3.6) |

### 3.5 承認リレー (R4 — コード完成・実地テスト待ち)

Claude Code が許可を求める → タチコマが**声で読み上げる** → 「はい/いいえ」を
STT → 判定を Claude Code へ返す。

- 実装: `notifier/tachikoma_notifier/` の `approval_store` / `permission_relay` /
  `voice_approval_gate` (268テスト通過)
- **音声で承認できるのは低リスク・読み取り専用ツールに限定**。拡大しない
- Even G2 と組むと、承認サマリを視界に出して R1 リングで承認できる

### 3.6 会社の体を繋ぐ (2026-08-19 完了)

```
会社の実機 → (会社LAN) → 会社PC の転送役 → (Tailscale) → 家のゲートウェイ
```

- ESP32 は Tailscale に入れないので、PC が経路の代わりをする
- 転送役 (`forwarder.py`) は**認証もしないし何も保存しない**。トークンも音声も
  素通しするので、**会社PCに API キーもトークンも要らない**。標準ライブラリのみ
- 会社PCでゲートウェイを起動してはいけない (記憶が枝分かれする)。
  タスク `Tachikoma Gateway` は**無効化済み**、`Tachikoma Forwarder` を
  ログオン時起動で登録済み
- 会社PCが起動していない間、会社の体は喋らない。**これは仕様**
- 実機に焼いてある URL は変えなくてよい (会社PCを指していれば転送役が引き受ける)

### 3.7 自前サーバ認証 (2026-07-28 完了)

M5Stack 公式アプリの認証は、公開ソースでは固定文字列を返すスタブだった
(本物は非公開バイナリ側)。同じ方式を mbedtls で実装し、自前の鍵と自前サーバで成立させた。

```
plain  = "<MAC>|<nonce>|<unix秒>"        3要素必須
cipher = RSA-OAEP(SHA-256, MGF1-SHA256, label なし, サーバ公開鍵)
header = Base64(cipher)                  2048bit なら 344 文字
```

タイムスタンプがサーバ時刻と **±10秒** を超えると拒否される。デバイス時計が
SNTP 同期していないと、実装が正しくても永久に 401 になる。
結果、**カメラ映像が中国のサーバを一切経由せずブラウザまで届く**ようになった。

## 4. 買い物系 (R9 モバイルオーダー) — 構想と現在地

### 構想

**「声で言うだけで、承認して、受け取りに行くだけ」**にする。マクドナルドは
**Phase 1 の1店目であって、目的ではない**。

```
Phase 0    iPhone ショートカット → GPS をゲートウェイへ            完了
Phase 1    マクドナルド: 音声→店舗検索→カート構築→承認→決済        決済直前まで完了
Phase 1.5  クーポン対応                                          未着手
Phase 2    モスバーガー / ケンタッキー                             未着手
Phase 3    スターバックス (プリペイドで最も安全)                    未着手
```

チェーンごとの差異は `mcd_adapter.py` のようなアダプタに閉じ込める設計。
**マックが恒久的に不調なら、Phase 1 の対象をモス/スタバへ乗り換える**判断が
既に用意されている (実際 2026-08-16 にマック Web版決済がサイト側障害と確定した)。

### 構成

`orderagent/` は**ゲートウェイと分離した別プロセス** (127.0.0.1:8766、Playwright 持ち)。
ゲートウェイ側は `order_bridge.py` (stdlib のみ、**エージェント停止時は完全に素通り**
= 通常会話に一切影響しない)。

### 決済の掟 (コードで強制済み)

- `ORDER_PAYMENT_ENABLED` 未設定 = **全ジョブがドライラン**
- 承認は**「注文」を含む明確なフレーズのみ**。「はい」単独では通らない。5分で失効
- 読み上げは**スクレイプしたカート実物**から生成する (推測で読まない)
- 明細と合計の完全突合 / 3,000円上限 / リトライ禁止 / CAPTCHA 即停止
- **実クリック部は意図的に未実装。** 実サイトの決済ページを大輔と一緒に
  ウォークスルーしてから実装する。盲目実装は禁止
- 決済手段はブラウザプロファイルに**大輔が手で登録**する。
  **エージェントは認証情報に触らない**

### 実地で掘り当てた事実 (変更検知の手がかり)

- マックWeb版の入口は隠されている。`/order` はアプリ誘導、**`/order/<店舗番号>` 直打ち**で
  SPA が開く (**モバイルUA必須**)
- 店舗検索は `map.mcdonalds.co.jp/api/poi` (全国2129店、key=店舗番号)。
  **Google Places 不要・APIキー不要**
- 価格は**店舗ごとに違う** (高鍋ハンバーガー190 vs 成田230)
- **カートは SPA メモリ内のみ**: `page.goto()` で消える → 商品間は pushState+popstate で遷移
- カート明細は DOM に**2重レンダリング** → 片方の UL のみ読む
- 明細スクレイプで**変更ボタンを目印にしてはいけない** — カスタマイズ不能商品
  (ポテト等) には変更ボタンが無く、静かに落ちる。目印は「¥価格＋数量の単独数字を持つli」
- 店舗お知らせモーダルが全クリックを吸う → 既知ラベルだけ自動クローズ
- 通称対応: 完全一致しない商品名は Gemini (`ai_match.py`) がメニュー実物から推測し、
  読み上げに「◯◯は△△のことだと解釈したよ」を**必ず前置**する (ダブチ→ダブルチーズバーガー)

## 7. 運用

### 起動 (家)

```powershell
powershell -File firmware\gateway\run_gateway.ps1
```

ログオン時に自動起動するタスク: `Tachikoma Gateway` / `VOICEVOX Engine (Tachikoma)` /
`Even Terminal` / `Tachikoma Order Agent`。

### 起動 (会社)

転送役**だけ**。ゲートウェイは起動しない。

```powershell
powershell -File firmware\gateway\run_forwarder.ps1
```

確認: `http://localhost:8080/healthz` が `{"ok":true}` を返すこと。

### テスト

```
python -m unittest gateway.test_server            # firmware/ から。51件
PYTHONPATH=notifier python -m unittest discover   # 268件
```

### 記憶の場所

`firmware/gateway/memory/` に `tachikoma.json` / `people.json` / `settings.json`。
**家のPCにしかない。git には入らない** (実名・居住地が入る)。
拠点間で運ぶときは `Z:\パーソナルフォルダ\タチコマ\記憶`。

## 8. 設計上の掟 (やってはいけないこと)

- **バックアップ無しで実機を焼く。** 16MBフルバックアップが 16,777,216 バイト
  ちょうどであることを確認してから焼く (460800 baud。921600 は失敗実績あり)
- **会社PCでゲートウェイを起動する。** 記憶が枝分かれし、時刻が無いため機械的に統合できない
- **NAS共有フォルダに記憶を置いてゲートウェイを2台走らせる。** `os.replace` の
  原子性が SMB では保証されず、片方の記憶が黙って消える。複数必要なら DB 化が先
- **`kFaceTrackingMovesHead` を `true` に戻す。** タッチセンサで押下と振動を
  区別できるまで戻さない。人が触っていないのに喋ってはいけない
- **顧客データを Gemini に渡す。** CRM は答えの文だけを返す方式を崩さない
- **git の SSL 検証を無効化する。** 証明書を参照させて解決済み
- APIキー・トークンをログ・音声・コミットに出す

### エージェントの運用ルール

- 実機flash・git push・シークレットの扱いは**実行前に必ず人間に確認**
- 修正は「観測→仮説→修正→実機ログで検証」。**勘で直さない**
- 受け入れ条件を満たすまで完了と報告しない
- ドキュメントは実装と同じコミットで更新する
- **毎セッション冒頭で必ず**「前回はここまで終わった」→「全体の中で現在ここ」→
  「今回はここから始める予定」の順で説明してから作業に入る (ダイスケの恒久指定)

## 10. 環境固有の落とし穴

| 罠 | 内容 |
|---|---|
| `pdMS_TO_TICKS(N)` | `CONFIG_FREERTOS_HZ=100` では `pdMS_TO_TICKS(5)` が **0** になり、`vTaskDelay(0)` = yield のみ。ウォッチドッグを踏む |
| PowerShell の `&&` | Windows PowerShell 5.1 には無い。`;` で区切る |
| .ps1 の文字コード | BOM無しUTF-8は Shift-JIS として読まれる。日本語リテラルが化ける |
| `Set-Content -Encoding utf8` | **BOM付き**で書く。Python 側は `utf-8-sig` で読むこと |
| pyserial で COM を開く | DTR/RTS がアサートされ **ESP32 が再起動する**。`dtr=False`/`rts=False` にしてから開く |
| `GATEWAY_HOST` の既定 | `127.0.0.1`。そのままではデバイスから繋がらない (`run_gateway.ps1` が `0.0.0.0` を強制) |
| `ESP_ERROR_CHECK` | コーデックのI2C失敗で即 `abort()`。一時的な失敗を致命的扱いしない |
| 素の `python` | ESP-IDF 同梱の Python に解決されることがある (torch/librosa/opencv 無し)。venv を PATH 先頭に |
| プロセスが静かに死ぬ | 終了コード `0xC000013A` は Ctrl+C/コンソール閉じ。**デスクトップの PowerShell 窓を閉じた巻き添え**が原因だった。コードを疑う前にマシンと窓を疑う |
