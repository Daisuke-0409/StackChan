# タチコマ 音声対話 — 2026-07-25〜26 作業サマリー

会話が成立しない状態から、記憶と検索を持つ実用的な音声対話まで。
ブランチ `phase4-ai-gateway`。

---

## 1. 返事が返ってこなかった

**原因**: ゲートウェイのプロセスが停止していた。デバイス側は正常だった。

デバイスに AI は載っておらず、返答はすべて PC 上の Tachikoma Gateway が生成する。
そのプロセスが落ちていると、デバイスは正しく録音・送信した上で接続を拒否される。

```
esp-tls: delayed connect error: Connection reset by peer
HTTP_CLIENT: Connection failed, sock < 0
TachikomaState: Thinking -> Error by AiRequestFailed
```

再発する構造だった点:

- `.env` が存在せず、起動のたびに環境変数を手打ちしていた
- `server.py` の `GATEWAY_HOST` 既定値が `127.0.0.1` で、そのまま起動するとデバイスから繋がらない
- Gemini API キーがマシン上のどこにも保存されていなかった

**対処**: `gateway/run_gateway.ps1` を追加。`.env` を読み、`0.0.0.0` を強制し、
`DEVICE_TOKEN` を `build/CMakeCache.txt` から補完し、キー未設定なら起動時点で停止する。
起動時に現在の LAN IP を表示（provisioned URL が固定 IP のため）。

## 2. 声は届くが内容が聞き取れない

**原因**: 録音ループがマイクの生成速度に追いついておらず、音声の約36%しか取得できていなかった。

| | |
|---|---|
| ハードウェアの生成量 | 24,000Hz × 2ch = **48,000 サンプル/秒** |
| ループの読み取り量 | 320サンプル ÷ 18.4ms = **17,391 サンプル/秒** |
| 実測レート | **8,313〜8,542Hz**（申告 24,000Hz） |

残りは DMA リング（1,440フレーム = 60ms分）から溢れて消失。
飛び飛びの断片が繋ぎ合わされ、約2.8倍速かつ音素の連続性が壊れた音声になっていた。

STT はこれを「誰かが喋った」とは認識できるが内容を復元できず、
`ご視聴ありがとうございました` のような**幻覚テキストを自信を持って返していた**。
これがそのまま質問として Gemini に送られるため、噛み合わない返答になっていた。

先に否定した仮説（すべて計測により棄却）:

| 仮説 | 検証 | 結果 |
|---|---|---|
| チャンネル残留 | 偶数/奇数サンプルの相関 | 否定（相関 +0.90〜0.97） |
| 4スロットTDM不一致 | スロット分離して再STT | 否定 |
| サンプルレート誤申告 | 8k/11k/16k/24k で再STT | 否定 |
| バイト順・ビット破損 | 全ビット出現率、重複率 | 否定（全ビット 0.50） |

**対処**: 読み取りサイズをマイクの実レート×チャンネル数から算出（20ms分 = 960）。
`esp_codec_dev_read` はブロッキング読みなので、録音中は `vTaskDelay` を廃止し、
読み取り自体にループのペースを作らせる。

**結果**: `measured_rate` が **22,528〜23,772**（申告24,000の94〜99%）。

## 3. レスポンスが遅すぎた（約14.6秒 → 約3.7秒）

**主犯**: `SpeechAnnouncer` が `Idle` 状態でしか返答音声を取得しない設計だった。
会話中は `Thinking` なので、文単位でストリーミングした音声がキューで待たされていた。
実測で、キュー投入から再生開始まで **6.9秒**放置されていた。

| 段階 | 修正前 | 修正後 | 手法 |
|---|---:|---:|---|
| STT | 4,890ms | **1,859ms** | `gemini-3.5-flash-lite` + 名前ヒント |
| チャット初文 | 735ms | 920ms | 変更なし |
| TTS | 2,047ms | **609ms** | ローカル VOICEVOX |
| 音声取得待ち | ~6,900ms | **~200ms** | Thinking/Speaking 中も取得、間隔200ms |
| **初音声まで合計** | **約14.6秒** | **約3.7秒** | **約4倍** |

補足:

- VOICEVOX はインストール済みだが起動していなかった。ゲートウェイに
  `TTS_PROVIDER=voicevox` を実装（エンジン停止時は Gemini に自動フォールバック）
- STT のプロンプトに「タチコマ」という名前を明示したところ、
  速いモデルの誤変換（「立ちコマ」）が解消し、かつ**さらに速くなった**（2,336ms → 1,859ms）

## 4. 会話を記憶しない

**原因**: `session_id` は返信でオウム返しされるだけで一切使われておらず、
リクエストごとに完全に独立した問い合わせになっていた。

**対処**: 2層構造。

| 層 | 内容 | 用途 |
|---|---|---|
| turns | 直近20メッセージ（10往復） | 「じゃあ明日は？」等の文脈解決 |
| profile | 名前・居住地・好み等の恒久的事実 | セッションをまたいで永続 |

profile の抽出は**返答送信後にバックグラウンドスレッドで実行**するため、
記憶処理が待ち時間に一切乗らない。

実測（4回の独立した HTTP リクエスト）:

```
> 俺の名前は大輔。覚えておいて。     < 大輔さんですね。しっかり覚えましたよ。
> 横浜市に住んでるよ。               < 横浜市にお住まいなのですね。
> 俺の名前は何だっけ？               < 大輔さんですよ。
> 今日の天気は？                     < 今日の横浜市は雲が広がっていますが…
```

最後の行が要点。**住所を言っていないのに地元の天気**が返っている。

## 5. ブラウジング（調べもの）

Gemini API 内蔵の Google 検索グラウンディングを使用。
スクレイピングも別の検索 API キーも不要。**ファーム変更なし**。

| 質問 | 検索 | 初文まで |
|---|---|---:|
| こんにちは | なし | 1,156ms |
| 今日の東京の天気は？ | あり（2クエリ/4ソース） | 1,719ms |
| 今の日本の総理大臣は？ | あり（1クエリ/1ソース） | 1,468ms |

**Gemini がリクエストごとに要否を判断する**ため、合言葉は不要で、
検索が不要な会話の速度は落ちない。

音声で使うための処理:

- システムプロンプトで箇条書き・記号・URL・絵文字を禁止（検索結果は既定でマークダウン）
- `_speakable()` ですり抜けた記号を合成直前に除去
- レスポンス解析を `parts[0]` 決め打ちから**全テキストパート連結**に修正
  （検索結果は複数パートに分割されるため、従来は回答が途中で切れる）

## 6. 録音時間 5.5秒 → 30秒

制限の正体は `kMaxRecordingSamples = 128*1024`。コメントには
「SpeechAnnouncer の kMaxAudioBytes に合わせた256KiB」とあったが、
それは**再生側の上限**で発話の長さとは無関係だった。

- 30秒 = 24kHz モノラルで 1.44MB → PSRAM（8MB）に配置
- 録音開始時に全量を先に確保（途中の再確保は旧＋新で2MB超の瞬間的消費を招く）
- 確保は空き PSRAM を問い合わせた上で `try/catch`。
  `CONFIG_COMPILER_CXX_EXCEPTIONS=y` のため、未捕捉の `bad_alloc` は
  長押し1回でデバイスを落とす
- HTTPタイムアウト 15秒 → 45秒

**実測**: 19.2秒の録音に成功。

## 7. 会話中に突然再起動する

**原因**: 処理落ちではなく `abort()`。

```
E I2C_If: Fail to read from dev 6c
ESP_ERROR_CHECK failed: esp_err_t 0x106 (ESP_ERR_NOT_SUPPORTED)
file: "cores3_audio_codec.cc" line 226
func: CoreS3AudioCodec::EnableOutput(bool)
expression: esp_codec_dev_open(output_dev_, &fs)
```

スピーカーアンプ(AW88298, 0x6C)への I2C 読み取りが一時的に失敗しただけで
`ESP_ERROR_CHECK` が即 abort → 再起動。同じ I2C バス上の FT6336 タッチ
コントローラも時折 `ESP_ERR_TIMEOUT` を出しており、この種の失敗は起こりうる。

1セッション中にクラッシュ2回、I2C失敗2回で**完全に1対1対応**。

**対処**: コーデックのオープン失敗を致命的扱いしない。1回リトライし、
それでも駄目なら警告を出して無効のまま戻る（次回クリーンに再試行できる）。
返答が1回再生されないのは復旧可能だが、再起動は復旧不可能。

## その他

- **名前の読み**: VOICEVOX が「大輔」を「オオスケ」と読む問題を、
  ユーザー辞書登録で解消。`gateway/voicevox_dict.json` に読みを保持し、
  ゲートウェイ起動時に再適用（エンジン再インストールでも失われない）
- **VOICEVOX 自動起動**: タスクスケジューラにログオン時起動を登録
  （`VOICEVOX Engine (Tachikoma)`）
- **フラッシュ前バックアップ**: 16MB フルバックアップを毎回取得。
  921600 baud でシリアル破損が起きたため 460800 に変更しリトライを追加
